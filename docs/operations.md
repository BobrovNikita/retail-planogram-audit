# Хранение, обслуживание и выпуск

## Корзина

В отчёте владельцу доступна кнопка «В корзину». Это обратимое действие: исходные данные, исправления и фото сохраняются, отчёт исчезает из основной истории, аналитики и дашборда. В корзине доступны просмотр, экспорт и восстановление. Редактировать детекции до восстановления нельзя. Все изменения требуют владельца, административной роли, CSRF и актуальной revision; старый запрос сохранения не создаёт дубль архивированной проверки.

`Retention:TrashDays` задаёт срок восстановления (по умолчанию 30 суток, допустимо 1–3650). Срок считается с момента перемещения в корзину, не с даты аудита. После восстановления и нового перемещения отсчёт начинается заново. До истечения срока окончательное удаление сервер запрещает. После срока пользователь может раскрыть действие «Удалить безвозвратно» и подтвердить его отдельным флажком.

`Retention:AutoPurge=false` по умолчанию: даже просроченные отчёты остаются до подтверждения. Если администратор сервера явно задаёт true, фоновое обслуживание при запуске и раз в час удаляет до 100 просроченных записей за проход. Активные проверки не удаляются автоматически. В Compose используются `RETENTION_TRASH_DAYS` и `RETENTION_AUTO_PURGE`; изменения требуют пересоздания app. Не сокращайте срок и не включайте автоочистку до резервного копирования и согласования политики хранения.

Отчёт, дочерние записи и задание удаления фото изменяются в одной транзакции. Если удалить файл сразу не удалось, запись остаётся в очереди; обслуживание повторит попытку. Очередь сохраняется при перезапуске. Только безопасные имена внутри audit-photos допускаются к удалению; используемые другими отчётами файлы не удаляются. Копии в черновиках имеют собственный срок, резервные копии обслуживаются отдельно. Корзина не освобождает место до окончательного удаления; SQLite может сохранять выделенный размер файла после удаления строк.

Перед миграцией AuditRetention сохраните backup. Старые отчёты получают ArchivedAtUtc=NULL и остаются активными. Используйте один экземпляр приложения, как предусмотрено текущей архитектурой.

## Ручная подготовка выпуска

В GitHub Actions выберите `Prepare deployment` → Run workflow. Workflow выполняет locked restore, build, тесты, Linux HTTPS/native/backup/restore, затем сохраняет артефакт на 14 дней: образ Docker linux/amd64, исходники точного коммита, SHA-256, IMAGE-ID и инструкцию.

Workflow имеет только contents:read, запускается вручную и не подключается к серверу. Адрес, SSH и секреты не выдумываются. Для установки скачайте артефакт и следуйте deploy/RELEASE.md. Настоящий deployment на VPS остаётся отдельным шагом после появления сервера и способа доступа.

## Ежедневные копии и проверки хоста

В deploy/systemd есть шаблоны backup (03:30 по времени сервера, случайная задержка до 15 минут) и проверки каждые 15 минут. Они пока не устанавливаются автоматически. Backup временно останавливает app; согласуйте время простоя. Скрипт использует flock, чтобы не запускать две плановые копии одновременно. Старые backup не удаляются автоматически.

На целевом Ubuntu-хосте создайте защищённый `/etc/retailvision/maintenance.env` со своими абсолютными путями:

```text
RETAILVISION_ROOT=/absolute/path/to/checkout
RETAILVISION_BACKUP_DIR=/absolute/path/to/private-backups
RETAILVISION_HEALTH_URL=https://your-domain/health
RETAILVISION_TLS_CERT=/absolute/path/to/tls/fullchain.pem
```

Если используете нестандартное имя Compose, задайте здесь тот же COMPOSE_PROJECT_NAME. Папка backup должна существовать, быть закрытой от других пользователей и иметь отдельную внешнюю копию. Файл окружения должен быть доступен только root. Для пути checkout с пробелами используйте допустимое для EnvironmentFile цитирование.

Скопируйте четыре unit-файла в /etc/systemd/system, выполните `systemctl daemon-reload`, вручную запустите `retailvision-backup.service` и `retailvision-check.service`. Только после успешной проверки включите таймеры через `systemctl enable --now retailvision-backup.timer retailvision-check.timer`. Диагностика: `systemctl --failed`, `journalctl -u retailvision-check.service`, `systemctl list-timers`.

Проверка контролирует HTTPS без отключения TLS-валидации, остаток сертификата минимум 7 дней, состояние контейнеров, наличие backup моложе 48 часов и свободное место (не менее 2 ГиБ и 10%) на файловых системах checkout, backup и Docker. При ошибке завершается ненулевым кодом и пишет в journal; внешние уведомления требуют отдельно выбранного канала. Это не нагрузочный тест и не проверка качества модели. На конкретном VPS ещё требуется проверить эти пороги, таймеры, выпуск/продление сертификата и доставку уведомлений.
