# Запуск и публикация

## Локально

Установите .NET SDK 10.0.400. Из корня solution:

```sh
dotnet restore --locked-mode
dotnet build -c Release
dotnet run --project src/RetailVision.Web -c Release --no-build
```

Адрес http://localhost:5180, только локальная привязка. Профиль Development указан в launchSettings. При запуске с `--no-launch-profile` задавайте `ASPNETCORE_ENVIRONMENT=Development` для локального HTTP; Production требует HTTPS. При первом запуске применяются миграции и seed. Python, GPU, ONNX-веса и администратор для DEMO не требуются.

Параметры среды:

| Ключ | Назначение |
|---|---|
| Storage__DataDirectory | Каталог SQLite, Data Protection keys и product-images вне wwwroot |
| Admin__Email | Email первого администратора, необязательный |
| Admin__Password | Секрет bootstrap, без значения по умолчанию |
| AllowedHosts | Разрешённые имена хоста; локально localhost;127.0.0.1 |
| ASPNETCORE_ENVIRONMENT | Development локально; Production на сервере |

## Резервное копирование и обновление локального экземпляра

1. Остановите приложение, чтобы закрыть SQLite и завершить запись.
2. Скопируйте целиком каталог данных, включая retailvision.db, возможные -wal/-shm, keys/ и product-images/, в защищённое хранилище. Для резервирования без остановки потребуется SQLite backup API, оно пока не реализовано.
3. Обновите исходники через обычный `git pull --ff-only`; не используйте force/reset для удаления локальных изменений.
4. Выполните restore, build и test. Запустите с тем же каталогом данных; миграции применятся без удаления базы.
5. Проверьте `/health`, каталог и DEMO. Для отката несовместимой схемы остановите приложение и восстановите вместе соответствующий код и резервную копию, а не одну старую DLL.

## VPS: ещё не реализованный этап 6

CatalogEditing перестраивает таблицу привязок классов для SQLite CHECK constraint. Не прерывайте применение миграции: SQLite/EF не гарантирует транзакционность всех операций перестройки. Перед обновлением нужна резервная копия. Тесты проверяют успешное обновление существующей схемы, но не восстановление после аварийного завершения.

Для изображений используются SkiaSharp и SkiaSharp.NativeAssets.Linux.NoDependencies закреплённой версии 4.153.1. Linux-зависимость включена в Web-проект; декодирование и перекодирование проверяются интеграционными тестами CI. Сборка Docker-контейнера остаётся отдельной задачей.

Целевая платформа — Ubuntu 24.04+, один .NET-процесс и SQLite на локальном постоянном томе, CPU-инференс с ограничением параллелизма. Потребуются multi-stage Dockerfile, непривилегированный пользователь, Compose, тома данных/моделей/загрузок, reverse proxy и HTTPS. Docker в текущей среде отсутствует; сборка контейнера не заявляется успешной.

До публикации должны быть заданы реальный домен, HTTPS-сертификат, безопасные секреты, корректные AllowedHosts и доверенные proxy-адреса. Нельзя слепо доверять forwarded headers от любого клиента. Текущий код специально не включает обработку произвольных proxy-заголовков; её нужно настроить и проверить вместе с Nginx, иначе HTTPS redirect за TLS-терминатором будет работать некорректно.

Публичный GitHub публикует исходники, а не сайт. Автоматического deployment workflow на неизвестный VPS нет. Эта версия не объявлена готовой к production.
