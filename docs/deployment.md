# Запуск и развёртывание

Целевая схема: один .NET-процесс, SQLite на локальном постоянном томе, Nginx с HTTPS. Контейнеры не требуют Python, GPU или весов для публичного DEMO. Подключение обученной SKU-модели отдельно описано в [ML-пайплайне](ml-pipeline.md). Публичного VPS у проекта пока нет: GitHub содержит исходники.

## Запуск без Docker

```sh
dotnet restore --locked-mode
dotnet build -c Release --no-restore
dotnet test -c Release --no-build
dotnet run --project src/RetailVision.Web -c Release --no-build
```

Требуется .NET SDK 10.0.400. Профиль Development слушает http://localhost:5180. При `--no-launch-profile` локальный HTTP требует `ASPNETCORE_ENVIRONMENT=Development`; Production перенаправляет страницы на HTTPS. `/health` доступен по HTTP для внутренней проверки контейнера и возвращает только состояние подключения к базе: 200 Healthy либо 503. Это readiness, а не проверка наличия обученной модели или свободного места.

## Образ и Compose

Dockerfile использует SDK 10.0.400 и ASP.NET runtime 10.0.11 на Ubuntu Noble, закреплённые по digest. Restore выполняется с lock-файлами; SDK остаётся в сборочном слое. Runtime содержит ICU для ru-RU, libgomp1, curl и зависимости приложения, включая SkiaSharp/ONNX Runtime. Сервис app работает как встроенный пользователь app (UID 1654), с read-only корнем, временным /tmp, без Linux capabilities. В образ не копируются локальные базы, фото, секреты или модели.

Compose сохраняет /data в именованном томе, /models монтирует только для чтения. Порт приложения 8080 не публикуется на хосте. Наружу доступны только порты Nginx: по умолчанию 127.0.0.1:8080 и 127.0.0.1:8443. Nginx — единственный доверенный proxy с конкретным IP; подсеть не добавляется в список доверия целиком. NETWORK_DYNAMIC_RANGE отделяет автоматически выдаваемые адреса от PROXY_IP. При конфликте подсетей измените NETWORK_SUBNET, NETWORK_DYNAMIC_RANGE и PROXY_IP вместе: адрес proxy должен быть внутри подсети и вне динамического диапазона.

Лимиты app: 2 CPU, 2 ГБ RAM, 256 процессов; Nginx: 128 МБ. Они являются исходной конфигурацией, а не результатом нагрузочного теста. Не масштабируйте app в несколько экземпляров: файловые хранилища и SQLite рассчитаны на один процесс. Логи Docker ограничены тремя файлами по 10 МБ на сервис.

## Локальная репетиция HTTPS на Linux

Нужны Docker Engine с Compose v2 и OpenSSL. Выполняйте из корня репозитория. Все команды ниже предполагают Bash.

```sh
cp .env.example .env
umask 077
openssl req -x509 -newkey rsa:2048 -sha256 -nodes -days 7 \
  -subj /CN=localhost -addext subjectAltName=DNS:localhost \
  -keyout deploy/tls/privkey.pem -out deploy/tls/fullchain.pem
docker compose config --quiet
docker compose up -d --build --wait --wait-timeout 150
curl --cacert deploy/tls/fullchain.pem https://localhost:8443/health
```

Откройте https://localhost:8443. Самоподписанный сертификат предназначен только для локальной репетиции; браузер не доверяет ему автоматически. Для публичного домена нужен действующий сертификат доверенного центра. DEMO работает без администратора и не сохраняет записи от посетителей. `docker compose logs --tail 100 app nginx` показывает диагностику, `docker compose stop` останавливает сервисы, `docker compose down` удаляет контейнеры/сеть, сохраняя том. **Не добавляйте `--volumes`/`-v` к down на экземпляре с нужными данными.**

## Первый администратор

Базовый Compose не создаёт администратора. Дополнительный compose.admin.yaml читает пароль из Docker secret, а не из образа или значения переменной окружения. Создайте закрытый файл с выбранным паролем (минимум 12 символов, верхний/нижний регистр, цифра и спецсимвол) и укажите в .env:

```dotenv
ADMIN_EMAIL=your-admin@example.com
ADMIN_PASSWORD_FILE=/absolute/protected/path/admin-password
```

Compose использует bind mount файла: назначение uid/mode в описании secret не заменяет права исходного файла. Владелец файла на Linux должен позволять UID 1654 читать его; например, `sudo chown 1654:1654 /absolute/protected/path/admin-password` и `sudo chmod 400 /absolute/protected/path/admin-password`. Родительский каталог ограничьте администратором хоста. Приложение убирает только завершающие CR/LF, не пробелы пароля. Файл и .env не должны попадать в Git или резервную копию для публичного доступа.

```sh
docker compose -f compose.yaml -f compose.admin.yaml up -d --wait --wait-timeout 150
# После успешного входа пересоздайте app без bootstrap-secret:
docker compose up -d --force-recreate --wait --wait-timeout 150
```

Существующая учётная запись не меняет пароль при следующем bootstrap. Сохраните пароль в менеджере паролей; секрет можно убрать из конфигурации после первого входа. При первом переходе с версии 0.5 на 0.6 потребуется повторный вход: Data Protection теперь имеет постоянное имя приложения RetailVision. Последующие пересоздания контейнера с тем же томом сохраняют ключи и действующие cookies.

## Публичный Linux-сервер

1. Установите Docker Engine/Compose по официальной инструкции для ОС. Клонируйте проверенный коммит проекта. Выделите локальный диск для тома и отдельное защищённое место для резервных копий.
2. Настройте DNS домена на VPS. В .env задайте DOMAIN, BIND_ADDRESS=0.0.0.0, HTTP_PORT=80, HTTPS_PORT=443 и уникальный IMAGE_TAG (например, SHA коммита). AllowedHosts приложения формируется из DOMAIN и локальных адресов для health check.
3. Получите действующий сертификат доверенного центра для DOMAIN. Укажите TLS_DIRECTORY — каталог, содержащий fullchain.pem и privkey.pem. Файлы должны быть доступны root-процессу Nginx. Не монтируйте только симлинки из Let's Encrypt live без их archive-целей: скопируйте действующие PEM в защищённый каталог либо обеспечьте доступность всей цепочки ссылок.
4. Запустите Compose, при необходимости с bootstrap-overlay. Проверьте HTTPS, вход, DEMO и `/health` с внешней машины. На firewall разрешите нужные публичные 80/443 и административный SSH; Kestrel не должен иметь публичного порта.
5. Настройте обновление сертификата у выбранного ACME-клиента/провайдера. После атомарной замены пары PEM выполните `docker compose exec -T nginx nginx -t` и `docker compose exec -T nginx nginx -s reload`. Выдача/автообновление сертификатов в этом репозитории не автоматизированы: владельцу нужно настроить их для своего домена.

Nginx перенаправляет HTTP на HTTPS, ограничивает тело запроса 10 МБ, проверяет Host и **перезаписывает** X-Forwarded-For/Proto входящего клиента. Приложение обрабатывает только эти два заголовка, только от указанного proxy, с лимитом один переход; X-Forwarded-Host не используется. `ASPNETCORE_FORWARDEDHEADERS_ENABLED=true` запрещён при старте, поскольку включает слишком широкое доверие. Добавление CDN/второго proxy требует отдельного изменения и проверки цепочки доверия. HSTS и Secure cookies включены в Production; HTTPS-перенаправление не применяется только к минимальному `/health`.

## Конфигурация приложения

| Ключ | Назначение |
|---|---|
| Storage__DataDirectory | SQLite, keys/, product-images/, photo-drafts/, audit-photos/ вне wwwroot; в контейнере /data |
| Vision__ManifestPath | Абсолютный путь manifest; в Compose VISION_MANIFEST_PATH=/models/manifest.json после установки обученных весов |
| Admin__Email | Email первого администратора |
| Admin__PasswordFile | Путь к bootstrap-secret, при создании нового администратора нельзя сочетать с Admin__Password |
| Admin__Password | Альтернатива для локального окружения/User Secrets; в Compose не используется |
| AllowedHosts | Список допустимых имён через `;` |
| Proxy__KnownProxies__0 | Конкретный IP доверенного proxy; без списка forwarded headers отключены |
| Proxy__HttpsPort | Внешний HTTPS-порт; по умолчанию 443, локальный Compose задаёт 8443 |
| ASPNETCORE_ENVIRONMENT | Development для локального HTTP; Production в образе |

Файлы обученной модели помещаются в MODELS_DIRECTORY на хосте, доступны UID 1654 для чтения. После смены manifest/весов пересоздайте app. Модель автоматически не загружается. Без неё доступен честно обозначенный DEMO, а реальное распознавание недоступно.

## Резервная копия и восстановление

Из корня checkout запустите `bash deploy/scripts/backup.sh /absolute/private/backup-directory`. Скрипт проверяет, что app работает, останавливает его с ожиданием до 45 секунд, архивирует весь /data через одноразовый контейнер, проверяет gzip и записывает SHA-256. Затем запускает исходный app, в том числе при ошибке копирования. Во время остановки Nginx может возвращать 502. Это согласованная копия с простоем; онлайн-резервирование SQLite не реализовано.

Архив включает базу (и возможные WAL/SHM), ключи cookies, товары, черновики и постоянные фото. Права создаваемых backup-файлов закрытые. Копируйте архив и .sha256 в отдельное защищённое хранилище; шифрование и срок хранения настраивает владелец. Модели, .env и TLS/административные секреты резервируются отдельно. Исходный образ/коммит нужно сохранить вместе с записью о версии backup.

Восстанавливайте только доверенный архив от backup.sh. Restore проверяет SHA-256 и gzip, требует остановленный app и пустой том; существующие данные не перезаписывает. Пример восстановления в новый Compose-проект, сохраняя старый том:

```sh
docker compose down                  # без -v; освобождает порты и подсеть
export COMPOSE_PROJECT_NAME=retailvision-restore
# Используйте образ/коммит, соответствующий копии, и тот же .env.
bash deploy/scripts/restore.sh /absolute/private/backup.tar.gz
docker compose up -d --wait --wait-timeout 150
```

Проверьте `/health`, вход, каталог, сохранённый отчёт и его фото. После успешного восстановления используйте выбранный COMPOSE_PROJECT_NAME во всех дальнейших командах и обновлениях; иначе Compose обратится к старому тому. Скрипт не удаляет старые тома и не выбирает backup автоматически. Если распаковка прервана, непустой частичный том будет отклонён при следующей попытке: создайте новый проект/том и сохраните неудачный для диагностики.

Без Docker остановите приложение и скопируйте целиком Storage__DataDirectory, затем восстановите его вместе с соответствующей версией приложения. Для обоих вариантов нужны все изображения и keys/, не только retailvision.db.

## Обновление и проверка

Перед обновлением сделайте backup, сохраните старый IMAGE_TAG/коммит и прочитайте миграции. Выполните `git pull --ff-only`, задайте новый IMAGE_TAG, затем `docker compose build --pull app` и `docker compose up -d --wait --wait-timeout 150`. Миграции применяются при старте. CatalogEditing и AuditHistory перестраивают таблицы SQLite; не прерывайте их выполнение. При несовместимой схеме откат — старый образ **вместе с полной резервной копией**, а не запуск старого кода поверх новой базы.

GitHub Actions отдельно проверяет .NET/Python и контейнер. Container job собирает final, запускает SkiaSharp/синтетический ONNX в отдельном verify-target на той же runtime-базе, поднимает настоящий Compose с временным TLS-сертификатом, проверяет DEMO, CSRF, Secure login, сохранённый отчёт и загрузку PNG. Затем проверяет пересоздание без bootstrap, восстановление в пустой том и отказ перезаписать непустой. Fixture и probe отсутствуют в final; это проверка исполнения, а не качества обученной модели. Конкретные успешные прогоны перечислены в [testing.md](testing.md).

На Windows этой рабочей среды Docker/рабочая WSL не установлены; контейнер проверяется на GitHub-hosted Ubuntu linux/amd64. ARM, реальный VPS, публичный сертификат/его продление и нагрузочные испытания не проверены. Активные проверки не удаляются автоматически. Для корзины есть защитный срок и отключённая по умолчанию автоочистка; см. [обслуживание](operations.md). Там же описаны ручной workflow выпуска и systemd-шаблоны backup/проверки хоста. Docker health status сам по себе не перезапускает нездоровый, но ещё работающий процесс; restart policy срабатывает при его завершении.
